# My First Pull Request, With a Side of Composer

[Composerpress](https://github.com/tomjn/composerpress) gave me a memorable: [pull request](https://github.com/tomjn/composerpress/pull/9). My first ever.

The project creates a `composer.json` for a WordPress site, bridging a WordPress installation and Composer.

The pull request collected several changes: documentation, fallback package naming, a configurable fallback namespace and a click-to-download feature. It was merged on April 5. A week later, I sent a [smaller fix](https://github.com/tomjn/composerpress/pull/10) for a PHP error that prevented the plugin from activating; that was merged too.

Alongside that, I reached out to a few neighboring WordPress projects. I opened an issue on [cedaro/satispress](https://github.com/cedaro/satispress/issues/29) about the package.json, the satispress\_packages\_json transient, and a SatisPress Repository URL not being found. I also opened two pull requests on [afragen/git-updater](https://github.com/afragen/git-updater): [one adding Rest Process logging](https://github.com/afragen/git-updater/pull/666) and [another with hook logging and UI improvement suggestions](https://github.com/afragen/git-updater/pull/668).

## A WordPress Site, Kept in Git

*Projects: 2018-04*

My [wordpress-git](https://github.com/Raruto/wordpress-git) repository dates back to April. Looking back, it brought together WordPress, Git, Composer and WP-CLI in a skeleton for managing a site.

The current guide describes declaring plugins and themes as Composer dependencies while keeping custom code under version control. It also points to [WP DevOps]({{ '/blog/2018-12-13-wp-devops-project.html' | relative_url }}) for generating a dependency list from an existing site. Check the repository before using it: this is a historical starting point, not a guarantee of compatibility with today's tooling.
