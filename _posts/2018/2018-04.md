# My First Pull Request, With a Side of Composer

[Composerpress](https://github.com/tomjn/composerpress) gave me a memorable first experience: my first ever [pull request](https://github.com/tomjn/composerpress/pull/9). The project creates a `composer.json` for a WordPress site, bridging WordPress and Composer.

The pull request collected several changes: documentation, fallback package naming, a configurable fallback namespace and a click-to-download feature. It was merged on April 5. A week later, I sent a [smaller fix](https://github.com/tomjn/composerpress/pull/10) for a PHP error that prevented the plugin from activating; that was merged too.

Alongside that, I reached out to neighboring WordPress projects. I opened an issue on [cedaro/satispress](https://github.com/cedaro/satispress/issues/29) about the package.json and the satispress\_packages\_json transient. I also opened two pull requests on [afragen/git-updater](https://github.com/afragen/git-updater): [one adding Rest Process logging](https://github.com/afragen/git-updater/pull/666) and [another with hook logging and UI improvements](https://github.com/afragen/git-updater/pull/668).

That same month, I brought a different part of the WordPress workflow into [wordpress-git](https://github.com/Raruto/wordpress-git): managing plugins and themes as Composer dependencies while keeping custom code under version control. The repository combines WordPress, Git, Composer and WP-CLI in a site-management skeleton, and points to [WP DevOps](https://github.com/Raruto/wp-devops) for generating dependency lists from an existing site. It's a historical starting point, so check its compatibility before using it with today's tooling.
